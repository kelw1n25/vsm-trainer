## 1. Что уже реализовано
Все 9 функциональных требований ТЗ реализованы в backend и веб-клиенте (см. [REQUIREMENTS_MATRIX.md](REQUIREMENTS_MATRIX.md)).
Бизнес-логика целиком на сервере: клиент не решает исход шага, не считает XP и рейтинг.

## 2. Что реализовано частично
- **Аутентификация для мобильных клиентов**: есть только access-токен на 12 ч, нет обновления сессии —
  на телефоне пришлось бы вводить пароль каждые 12 часов.
- **Аналитика**: нет среднего времени решения и доли завершённых сценариев; не фиксируются
  выход из сценария без финала, открытие разбора и открытие уведомления.
- **Обработка ошибок**: единый формат для 4xx есть, но непредвиденное исключение отдаёт стандартный ответ
  FastAPI без кода ошибки и без идентификатора запроса.
- **Логирование**: текстовые строки, нет идентификатора запроса и журнала аудита входов.
- **Уведомления**: только внутри приложения (опрос); push-доставки нет.

## 3. Что отсутствует
- iOS-приложение (Swift/SwiftUI) и Android-приложение (Kotlin/Compose).
- `POST /api/auth/refresh`, `POST /api/auth/logout`.
- Ограничение частоты попыток входа (было указано в ограничениях как известный пробел).
- OpenAPI-файл в репозитории (схема отдавалась только живым сервером).
- CI.

## 4. Что необходимо переписать
Ничего. Backend — production-пригодный стек (FastAPI + PostgreSQL + миграции), бизнес-логика покрыта тестами.
Веб-клиент остаётся как есть: мобильные приложения — дополнительные клиенты того же API.

## 5. Что необходимо адаптировать
| Что | Минимальное изменение |
|-----|----------------------|
| Сессии | refresh-токены с ротацией и отзывом (таблица `refresh_tokens`, миграция `0005`) |
| Вход | ограничение частоты попыток, `429 too_many_attempts` + `Retry-After` |
| Ошибки | обработчик непредвиденных исключений: `500 internal_error` без стека, с `request_id` |
| Логи | JSON-строка на запрос с `request_id`, журнал аудита входов без ПДН |
| Аналитика | клиентские события `debrief_opened`, `notification_opened`, `run_exited`; метрики `avg_decision_seconds`, `completion_rate` |

## 6. Какие модули переиспользуются
Все модули backend без изменения поведения: `engine`, `scenarios`, `scoring`, `achievements`, `leaderboard`,
`notifications`, `analytics`, `profiles`, `handbook`, `integration`. Формат ошибок `{"detail": {"code", "message"}}`
используется мобильными клиентами как есть: они ветвятся по `code`, а `message` показывают пользователю.
Протокол прохождения (`POST /api/runs` → `reveal` → `choices` → `debrief`) переносится в мобильные клиенты один к одному.

## 7. Технические риски
| Риск | Как учтён |
|------|-----------|
| На машине разработки нет Xcode — iOS-таргет нельзя собрать локально | ядро iOS — Swift-пакет: тесты гоняются в Docker `swift:6.1` (Linux), SwiftUI-слой компилируется `swift build` на macOS; полная сборка iOS-таргета — в CI на `macos-latest` |
| Нет JDK и Android SDK | сборка и тесты Android в Docker-образе `android/ci/Dockerfile` |
| Часы телефона расходятся с сервером — таймер покажет не то | клиент считает остаток от `server_time` из ответа, решает всё равно сервер |
| Двойное нажатие / повтор запроса при плохой сети | сервер отклоняет повтор кодом `stale_node`; клиент перечитывает состояние |
| Приложение закрыли посреди сценария | состояние целиком на сервере; `POST /api/runs` возвращает незавершённое прохождение |
| Ограничение частоты входа в памяти процесса | при нескольких копиях backend лимит считается на копию — зафиксировано в SECURITY.md |

## 8. Используемые зависимости
- Backend: fastapi, uvicorn, sqlalchemy, alembic, psycopg, pydantic-settings, pyyaml, pyjwt; тесты — pytest, httpx2.
- Frontend: react, react-dom, react-router, recharts; сборка — vite, typescript.

## 9. Какие зависимости заменить
Никакие. Для refresh-токенов, лимита входа и логирования новые зависимости не нужны — хватает стандартной библиотеки
(`secrets`, `hashlib`, `logging`, `json`).

## 10. Что соответствует ТЗ
Функциональные требования 1–9, API для HR/LMS/биллинга, Docker, README, синтетические данные, отсутствие секретов в Git
(`.env` в `.gitignore`, в `.env.example` — только демо-значения).

## 11. Что не соответствует ТЗ / брифу мобильной версии
- Нет мобильных клиентов (бриф требует нативные iOS и Android).
- Нет CI (бриф: lint → test → build).
- Нет ограничения частоты входа и refresh-токенов (бриф, раздел SECURITY).
